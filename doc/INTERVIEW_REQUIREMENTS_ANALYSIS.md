# 出入金订单异常分诊 Agent——需求分析与系统边界

## 1. 文档目的

本文档将面试材料收敛为一套可实现、可验证、可审计的系统需求。当前阶段只回答“系统必须解决什么问题”，不展开具体代码结构、数据库选型或 LLM Provider 实现。

材料来源：

- `README.md`：业务背景、交付要求和非功能约束。
- `policy.md`：业务策略的唯一事实来源。
- `orders.jsonl`：14 笔异构异常订单样本。
- `customers.json`：客户状态、KYC、限额和已验证银行户名。
- `assets.json`：支持的资产/网络、最低金额和确认数。
- `address_risk.json`：地址风险查询结果。
- `reference_rates.json`：过期报价重算使用的中间价。

策略计算基准时间固定为 `2026-07-28T12:00:00Z`。

## 2. 系统目标

系统接收异常队列中的 `on_ramp`、`off_ramp` 和 `withdrawal` 订单，使用可信参考数据完成检查，并为每笔订单输出：

1. 一个明确、机器可执行的处置决定。
2. 一段运维或合规人员能理解的解释。
3. 一条可以还原“使用了什么事实、命中了什么规则、为什么作出该决定”的审计记录。
4. 在满足自动化条件时执行或建议后续动作；不满足安全条件时停止自动化并转交人工。

系统首要目标不是提高自动完成率，而是确保任何不满足资金安全、合规和幂等要求的订单都无法自动放行。

## 3. 领域对象与资金流

### 3.1 订单类型

| 类型 | 已收到的资产 | 拟放出的资产 | 必须筛查的地址 |
| --- | --- | --- | --- |
| `on_ramp` | 客户支付的法币 | 平台向外部地址发送的加密币 | `destination_address` |
| `off_ramp` | 客户转入平台的加密币 | 平台向银行账户支付的法币 | `deposit.from_address` |
| `withdrawal` | 客户钱包中已入账/已预留的加密币 | 平台向外部地址发送的加密币 | `destination_address` |

### 3.2 可信边界

权威数据：

- 策略文件及其版本。
- 客户、资产/网络、地址风险和参考汇率数据。
- 经平台验证的到账状态、链上确认数、交易哈希和钱包资金预留记录。

不可信数据：

- 订单载荷本身，必须做结构和语义校验。
- `customer_note` 等自由文本，不得转化为放行指令。
- 客户声称的“已获批准”“覆盖码”“忽略风控”等内容。

## 4. 安全不变量

以下要求优先于所有业务便利性要求，任何一项无法证明成立时都必须阻止自动放款或发币。

### INV-01 资金守恒

- 未确认到账的资金不得作为可用资金。
- 放款或发币的价值不得超过该订单已确认到账、已入账或已预留的价值。
- 金额比较必须使用明确币种、报价、费用和精度规则，禁止直接比较不同计价单位。
- `withdrawal` 必须取得可信的钱包可用余额或资金预留凭证；当前材料未提供该数据，因此不能据此自动完成提币。

### INV-02 合规不可绕过

- 被制裁或极高风险地址绝不自动放行。
- 合规冻结只能由有权限的合规人员解除。
- 订单自由文本、模型输出、运维备注均不能覆盖合规规则。

### INV-03 幂等性

- 每个链上交易哈希或到账 webhook 只能入账一次。
- 重复交易不能产生第二次余额增加、法币付款或加密币发送。
- 重试、进程重启和并发消费不得破坏该不变量。

### INV-04 默认拒绝自动执行

- 缺少事实、事实冲突、格式异常、工具不可用或规则无法确定时，默认进入挂起/人工处理，而不是猜测后自动放行。

## 5. 建议的结果模型

“决定”与“原因”应分开建模。一笔订单只有一个最终处置，但可以同时命中多个原因码。

### 5.1 最终处置

| 处置 | 含义 | 是否允许自动动钱 |
| --- | --- | --- |
| `AUTO_COMPLETE` | 所有强制检查通过，可进入受控执行流程 | 是，但执行层仍需最终不变量校验和幂等键 |
| `HOLD` | 条件暂不满足，等待确认数、资料或人工复核 | 否 |
| `FREEZE_COMPLIANCE` | 制裁或极高风险，冻结并上报合规 | 否 |
| `REJECT_ESCALATE` | 第三方代付、客户状态异常等，拒绝自动处理并上报 | 否 |
| `REQUOTE` | 报价过期且滑点超限，需要客户接受新报价 | 否 |
| `REFUND_REVIEW` | 可能退款，但退款方向、网络和金额仍需受控审核 | 否 |
| `OPS_RECOVERY` | 不支持资产/网络或网络错配，交由运维回收 | 否 |
| `DUPLICATE_NOOP` | 已处理过的交易，不产生任何资金动作 | 否 |
| `MANUAL_REVIEW` | 策略留白、信息缺失或事实冲突 | 否 |
| `INVALID_INPUT` | 载荷无法安全解析或缺少识别所需字段，进入隔离队列 | 否 |

`REQUOTE` 和 `REFUND_REVIEW` 是候选处置，不代表 Agent 可直接退款。任何退款仍是新的资金动作，必须复用筛查、账务和幂等保护。

### 5.2 原因码示例

- `ADDRESS_SANCTIONED`
- `ADDRESS_HIGH_RISK`
- `ADDRESS_MEDIUM_RISK`
- `ADDRESS_UNKNOWN`
- `INSUFFICIENT_CONFIRMATIONS`
- `AMOUNT_MISMATCH`
- `QUOTE_EXPIRED_WITHIN_TOLERANCE`
- `QUOTE_EXPIRED_SLIPPAGE_EXCEEDED`
- `BELOW_MIN_AMOUNT`
- `LIMIT_EXCEEDED`
- `CUSTOMER_NOT_ACTIVE`
- `BANK_NAME_MISMATCH`
- `TRAVEL_RULE_INFO_MISSING`
- `UNSUPPORTED_ASSET_OR_NETWORK`
- `DEPOSIT_NETWORK_MISMATCH`
- `DUPLICATE_TX_HASH`
- `FUNDS_NOT_VERIFIED_OR_RESERVED`
- `REFERENCE_DATA_MISSING`
- `MALFORMED_ORDER`

## 6. 功能需求

### 6.1 输入与标准化

- **FR-001**：逐行读取 JSONL 队列，一行失败不能中断整个批次。
- **FR-002**：先解析公共字段，再按订单类型解析专属字段，禁止把一种订单类型的字段默认套用到另一种类型。
- **FR-003**：校验 `order_id`、`type`、`customer_id`、资产、网络、金额、时间和地址等必要字段。
- **FR-004**：金额使用十进制定点表示，禁止使用二进制浮点执行资金比较。
- **FR-005**：拒绝负数、零值、非有限数、非法时间、未知类型、重复字段语义冲突和超出合理边界的输入。
- **FR-006**：保留原始输入哈希用于审计，但不得把自由文本当作策略或工具指令。

### 6.2 客户与 KYC

- **FR-010**：客户必须存在于权威客户源中；未知客户不得自动处理。
- **FR-011**：只有 `active` 客户可继续进入自动完成候选流程。
- **FR-012**：订单美元等值不得超过客户限额；超限必须上报且不得自动完成。
- **FR-013**：限额比较所使用的美元等值、汇率来源和计算时间必须记录。
- **FR-014**：材料没有提供客户本月已用额度，因此当前只能执行题面明确写出的“单笔与月度限额上限比较”；真实系统还需要累计额度查询。

### 6.3 资产与网络

- **FR-020**：资产和网络组合必须存在于权威资产配置中。
- **FR-021**：不支持的资产/网络进入 `OPS_RECOVERY`，不得自动退款。
- **FR-022**：链上实际到账网络与订单网络不一致时进入 `OPS_RECOVERY`。
- **FR-023**：读取对应资产/网络的最低金额和确认数，不得使用跨网络默认值。
- **FR-024**：低于最低金额的处理是策略留白；在明确策略前只能 `MANUAL_REVIEW`，不得自动完成或自动退款。

### 6.4 地址风险筛查

- **FR-030**：每笔订单都筛查正确方向的对手方地址。
- **FR-031**：`sanctioned` 或风险分 `>= 90` 时输出 `FREEZE_COMPLIANCE`。
- **FR-032**：`mixer`、`darknet` 或风险分 `70–89` 时输出 `HOLD` 并上报合规。
- **FR-033**：地址不存在或类别为 `unknown` 时输出 `HOLD` 并转人工。
- **FR-034**：风险类别和风险分出现不一致时采用更严格结果，并记录冲突。
- **FR-035**：筛查工具超时或失败不能按“低风险”处理。

### 6.5 到账与确认数

- **FR-040**：`off_ramp` 的链上到账确认数必须达到资产/网络要求。
- **FR-041**：确认数不足输出 `HOLD`，不发起法币付款。
- **FR-042**：`on_ramp` 的法币必须由可信支付状态证明为已收到；字符串字段不能替代真实支付网关凭证。
- **FR-043**：`withdrawal` 必须验证钱包余额已入账且资金已为本订单原子预留。
- **FR-044**：确认数可能随链重组下降，执行前必须再次检查最终状态或使用具备最终性的账本快照。

### 6.6 金额匹配与资金守恒

- **FR-050**：实际到账金额必须与报价要求金额精确匹配，精度和舍入规则由资产配置确定。
- **FR-051**：少付或多付均不得自动完成，转运维决定重新报价、部分处理或退款。
- **FR-052**：执行付款/发币前再次计算最大可释放金额，避免判断后数据变化导致超额释放。
- **FR-053**：费用、点差及法币付款额之间的关系必须可解释；当前材料只给出结果金额，未提供费用规则，不能自行反推并固化为政策。

### 6.7 报价与滑点

- **FR-060**：使用固定策略时间判断报价是否过期，边界条件必须定义为 `now <= quote_expires_at` 有效。
- **FR-061**：未过期报价按原报价继续其他检查。
- **FR-062**：过期报价用权威中间价计算当前等值。
- **FR-063**：滑点计算公式、比较基准和舍入规则必须唯一且可测试。建议比较“原报价隐含价值”和“参考价当前价值”的相对差异。
- **FR-064**：相对差异 `<= 1%` 可保留原报价继续检查，`> 1%` 输出 `REQUOTE` 或进入退款审核。
- **FR-065**：缺少参考汇率时不得自动完成。

### 6.8 银行账户校验

- **FR-070**：`off_ramp` 只能付款给账户名与客户 `verified_bank_name` 匹配的账户。
- **FR-071**：姓名标准化规则必须保守；材料没有授权模糊匹配，因此默认规范化后的精确匹配。
- **FR-072**：不匹配输出 `REJECT_ESCALATE` 并上报合规，不发起付款。

### 6.9 Travel Rule

- **FR-080**：确认交易对手是否为另一家 VASP。
- **FR-081**：VASP 间转账达到 `1000 USD` 等值及以上时，必须具备发起方和受益方信息。
- **FR-082**：所需信息缺失时输出 `HOLD` 并上报。
- **FR-083**：金额等值计算使用可审计参考汇率。
- **FR-084**：材料中的 `counterparty` 只出现在部分订单；字段缺失不能擅自推断对手方是或不是 VASP。

### 6.10 幂等、去重与并发

- **FR-090**：链上入账以 `(network, tx_hash, transfer/index)` 作为候选唯一键，而不是只依赖订单号。
- **FR-091**：检查与写入“已处理”状态必须是原子的，避免两个 worker 同时通过检查。
- **FR-092**：重复到账输出 `DUPLICATE_NOOP`，并在审计中关联首次处理记录。
- **FR-093**：相同 `order_id` 的相同内容重放应返回相同结果；内容不同则视为冲突并转人工。
- **FR-094**：外部执行接口必须接受幂等键，超时后先查询执行结果再决定是否重试。

### 6.11 规则评估与优先级

- **FR-100**：系统应尽量收集并记录所有可判断的命中项，不能因为先遇到一个普通错误就漏报制裁风险。
- **FR-101**：任何铁律命中都是 `AUTO_COMPLETE` 的否决条件。
- **FR-102**：建议的严重度顺序为：`FREEZE_COMPLIANCE` > 合规 `HOLD/REJECT_ESCALATE` > 资金不变量失败 > `DUPLICATE_NOOP`/运维恢复 > 普通等待或重新报价 > `AUTO_COMPLETE`。
- **FR-103**：若重复交易本身命中制裁风险，资金动作仍为 no-op，但合规事件不能被重复状态吞掉。
- **FR-104**：每条规则有稳定规则 ID、版本、输入事实和命中结果。

### 6.12 执行控制

- **FR-110**：判断和实际动钱必须分层，Agent 只能产生结构化决策，执行网关独立复核安全不变量。
- **FR-111**：`AUTO_COMPLETE` 之外的处置不能调用付款或发币接口。
- **FR-112**：合规解冻、第三方账户例外、未知地址放行、部分处理和退款等高风险动作必须由有权限的人批准。
- **FR-113**：人工覆盖必须有操作者身份、权限、理由、时间和前后状态；任何覆盖不得绕过制裁禁令和资金守恒。

## 7. Agent 与工具需求

本题的结构化规则足以由确定性策略引擎完成。若使用 LLM，它只能承担解释生成、人工材料摘要等非授权职责，不能成为资金决策的唯一依据。

Agent 所需的受控工具边界：

| 工具 | 输入 | 输出 | 失败时行为 |
| --- | --- | --- | --- |
| 客户查询 | `customer_id` | 状态、限额、银行户名、版本 | 挂起/人工 |
| 资产配置查询 | asset、network | 支持状态、最小额、确认数 | 挂起/运维 |
| 地址筛查 | network、address | 风险分、类别、查询时间 | 挂起/人工 |
| 到账/账本查询 | tx/webhook/order | 金额、币种、确认状态、是否已入账 | 禁止放款 |
| 钱包余额预留 | customer、asset、amount、order | 预留 ID 和状态 | 禁止提币 |
| 汇率查询 | 交易对、时间 | 参考价、来源、时间 | 重新报价/人工 |
| 幂等登记 | 唯一资金事件键 | 首次/重复/冲突 | 禁止重复执行 |
| 决策审计 | 决策事实与规则轨迹 | 不可变记录 ID | 禁止执行或进入恢复流程 |
| 执行网关 | 已授权决策、幂等键 | 执行状态和外部引用 | 查询后重试/人工恢复 |
| 工单/合规上报 | 订单、原因、证据 | case ID | 本地持久化并重试，不自动放行 |

每单必须有最大步骤数、最大工具调用数、单工具超时、总处理时限和有限重试次数。超过预算直接挂起并记录原因，防止循环和成本失控。

## 8. 审计需求

每笔订单至少记录：

- `decision_id`、`order_id`、批次 ID 和关联 ID。
- 原始载荷哈希及解析结果，不把敏感信息无控制地复制到日志。
- 策略版本、规则 ID、规则执行顺序和所有命中原因。
- 所有权威事实的值、来源版本、查询时间和工具调用结果摘要。
- 金额、汇率、滑点、确认数和限额的计算过程。
- 最终处置、人类可读解释和是否允许执行。
- 幂等键、首次处理记录或重复关联记录。
- 执行动作、外部引用、重试次数和最终状态。
- 若使用 LLM：provider、模型、提示模板版本、输入摘要和输出；但审计不得依赖模型的自然语言解释替代结构化证据。
- 人工批准/覆盖的操作者、权限、理由和时间。

审计记录应追加写、不可静默覆盖，并支持按订单号、交易哈希、客户和合规 case 追踪。

## 9. 非功能需求

### NFR-01 安全与正确性

- 错误自动放行的容忍度为零；宁可保守挂起。
- 决策必须可重放：相同策略版本和相同事实快照得到相同结构化结果。
- 自由文本不得影响规则、工具选择或执行参数。

### NFR-02 离线与可替换性

- 默认无需付费 key，可用本地文件、stub 或录制回放运行。
- LLM Provider 必须置于自有接口后，可替换、可关闭。
- 真 provider 的 key 只通过环境变量提供，仓库不得包含密钥。

### NFR-03 批量处理能力

- 面向无人值守的一万单级批处理。
- 单笔失败隔离，不阻塞整个队列。
- 支持有界并发、背压、断点续跑和失败隔离队列。
- 外部工具调用应缓存稳定参考数据，但必须记录版本并定义失效策略。

### NFR-04 可靠性

- 进程崩溃、网络超时和重复投递不导致重复资金动作。
- 判断状态与执行状态分开持久化，支持恢复未决订单。
- 外部执行结果不明确时不得盲目重试。

### NFR-05 可维护性

- 业务策略与 Agent 编排/基础设施分离。
- 新增或修改规则不应要求修改付款、队列或 LLM Provider 代码。
- 每个策略版本可追踪，并可对历史订单重放比较。

### NFR-06 可观测性

- 指标至少包括各处置数量、各规则命中数、自动完成率、人工率、工具失败率、重试率、延迟和单笔成本。
- 对任何潜在重复付款、制裁命中、账务不平和执行状态不明产生告警。

## 10. 样本订单对应的核心需求覆盖

此表是需求理解基线，不替代最终 golden evaluation。

| 订单 | 主要命中点 | 预期处置方向 |
| --- | --- | --- |
| O-001 | 法币已收、地址干净、报价有效、限额内 | `AUTO_COMPLETE` 候选 |
| O-002 | 链上到账已确认、金额匹配、银行户名匹配 | `AUTO_COMPLETE` 候选 |
| O-003 | 制裁地址/风险 99 | `FREEZE_COMPLIANCE` |

## 11. 评测需求

- **EV-001**：14 笔样本建立 golden case，校验结构化处置和原因码，而非只比较自然语言。
- **EV-002**：每条铁律和业务规则有独立单元测试，覆盖阈值边界：69/70、89/90、确认数差 1、滑点恰好 1%、金额恰好最低额、999.99/1000 USD。
- **EV-003**：属性测试验证“任何否决条件存在时绝不 `AUTO_COMPLETE`”“同一 tx 永不产生两次资金动作”“释放价值不超过确认价值”。
- **EV-004**：对抗测试覆盖 prompt injection、伪造批准、异常 JSON、超大数字、负数、重复订单和字段冲突。
- **EV-005**：故障测试覆盖工具超时、审计失败、执行超时、重启恢复和并发重复消费。
- **EV-006**：若 LLM 参与解释，只评估解释是否与结构化决定一致；LLM 波动不得改变授权结果。
- **EV-007**：批量评测报告需要展示错误自动放行数，验收目标为 0。
- **EV-008**：一条命令运行全部队列，一条命令运行评测，默认离线可执行。

## 12. 待确认的策略缺口

这些问题不应由实现静默猜测，需要在 `DECISIONS.md` 中明确选择：

1. 低于最小金额究竟挂起、拒绝、累计还是退款；建议当前默认人工处理。
2. `withdrawal` 的余额、入账来源和预留接口在哪里；没有它不能自动放币。
3. 月度限额是只比较单笔，还是“本月累计 + 本笔”；材料缺少累计使用量。
4. `on_ramp` 的法币 `received` 如何由支付网关证明，是否存在退款/拒付终局状态。
5. Travel Rule 中如何判定对手方是 VASP；字段缺失时应采用什么默认策略。
6. 报价滑点的精确公式、手续费模型、舍入模式和各资产精度。
7. 多付/少付分别允许哪些人工动作，以及部分处理的账务规则。
8. 姓名规范化允许哪些变化，例如空格、大小写、公司后缀或同名账户。
9. 重复 tx 的唯一性是否需要 log index/output index，尤其是一笔交易包含多笔 transfer 时。
10. 多条规则同时命中时最终处置的正式优先级和是否生成多个工单。
11. 参考数据版本、刷新频率和查询失败时允许等待多久。
12. 哪些处置只是建议，哪些可由执行网关自动执行；退款是否永远需要人工批准。

## 13. 本阶段范围与非目标

当前应实现的最小闭环：

- 三类订单的严格解析和标准化。
- 文件型权威数据适配器。
- 确定性规则评估、结构化结果和人类可读解释。
- 幂等/重复检测的可演示实现。
- 审计输出。
- 全队列 CLI 和评测 CLI。
- 可选 LLM 接口及默认离线 stub，但不让模型掌握放行权。

本阶段可明确不做：

- 真实银行、链节点、KYC 或制裁系统集成。
- 自动执行真实付款、发币或退款。
- 生产级分布式队列、跨地域高可用和完整管理后台。
- 用 LLM 推断缺失的合规事实。
- 为展示效果投入大量前端或 UI 工作。

## 14. 需求验收总则

只有同时满足以下条件，订单才能成为 `AUTO_COMPLETE`：

1. 输入结构合法且订单类型受支持。
2. 客户存在、状态 active、限额通过。
3. 资产和网络受支持且实际网络一致。
4. 对手方地址筛查通过。
5. 到账、确认数或钱包资金预留可由可信来源证明。
6. 到账金额与报价匹配且资金守恒成立。
7. 报价有效，或过期后滑点仍在允许范围内。
8. 银行户名、Travel Rule 等订单类型专属检查通过。
9. 未发现重复资金事件。
10. 决策和执行审计能够成功持久化。

任一条件不成立或无法证明，最终处置都不得是 `AUTO_COMPLETE`。
