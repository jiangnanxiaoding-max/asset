# 关键设计决策

本文记录影响资金安全、可审计性和可扩展性的关键取舍。每项都说明最终选择、被放弃的方案及原因。

## 1. 核心采用确定性 Agent，不让 LLM 编排资金调查

### 最终选择

核心队列使用确定性工作流：

```text
解析订单
→ 查询固定的权威事实
→ 执行确定性领域规则
→ 聚合决定
→ 写入审计
→ 输出结果或创建人工工单
```

这里的 Agent 是能够自主完成“感知、判断、行动、停止”的业务执行者，但不是 LLM：

- 感知：通过 Port 查询客户、资产网络、地址风险、资金、汇率和 Travel Rule 等事实。
- 判断：由版本化领域规则产生结构化 `RuleResult`。
- 行动：输出决定、写审计、创建人工或合规工单。
- 停止：事实充分时判定；事实冲突、工具不可用或安全条件不满足时转人工或挂起。

### 砍掉的备选方案

砍掉“让 LLM 每轮决定调用哪个调查工具，并编排核心资金审核”的方案。

原因：

1. 工具集合、订单类型分支和前置依赖都是提前已知的，用固定 DAG 比模型规划更简单。
2. LLM 不能创造钱包余额、银行到账、链上确认或制裁名单等权威事实。
3. 相同事实和策略必须稳定重放；模型版本、Prompt 和随机性会增加复现成本。
4. 上万单无人值守运行时，LLM 会增加延迟、Token 成本、限流、超时和 Provider 故障点。
5. 订单内容是不可信输入，让模型阅读原始备注会扩大 Prompt injection 攻击面。
6. 这是资金业务，错误自动放行的损失远大于慢一点或多转人工。

### LLM 的保留边界

仓库可以保留隔离的 `LlmAgentClient`、Stub、Replay、HTTP Provider、预算和超时实现，作为技术演示或未来实验，但它不应成为默认资金决策链路的必要依赖。

LLM 未来只适合：

- 总结人工审核材料；
- 从非结构化文件提取候选字段，再由确定性逻辑校验；
- 将结构化原因转换为更友好的人类说明；
- 给审核员推荐调查方向，但不能直接批准订单；
- 帮助起草策略变更，必须经过人工审批和回归评测。

无论是否使用 LLM，都必须满足：

```text
LLM 不能生成最终 TriageDecision
LLM 不能绕过领域规则
LLM 不能直接执行资金动作
LLM 失败不能使决定变得更宽松
```

### 当前实现的对齐状态

当前代码中的 LLM Adapter 已做到工具白名单、服务端绑定参数、硬超时、重试、Token/并发预算、熔断和运行审计，最终决定仍由确定性规则产生，因此没有突破资金安全边界。

但默认运行时目前仍会在出现 `UNAVAILABLE/CONFLICT` 时使用离线 Stub 做一次受控补查。这不会改变最终安全结果，却会增加无业务收益的编排复杂度。最终交付前应让默认运行时直接使用 `DefaultInvestigationService`，将 LLM Adapter 留作独立 Demo 和测试入口。

## 2. 最终决定只能由结构化事实和领域规则产生

### 最终选择

调查阶段只生成强类型 `InvestigationFacts`；领域规则是纯计算，不执行 I/O；`DefaultDecisionAggregator` 根据全部规则结果聚合最终处置。

### 砍掉的备选方案

没有采用以下方案：

- 让模型直接返回 `AUTO_COMPLETE`、`HOLD` 等处置；
- 根据自然语言理由反推决定；
- 将外部 Provider 的风险分数未经领域规则解释就直接作为最终结论。

原因是这些方案难以稳定重放、版本化和审计，也无法结构性保证高风险决定永不自动执行。

## 3. 不确定性必须 fail-closed

### 最终选择

外部查询使用 `LookupResult` 明确区分：

- `Found`：取得权威事实；
- `NotFound`：权威系统明确没有记录；
- `NotApplicable`：当前订单不需要此事实；
- `Unavailable`：工具失败、超时或预算耗尽；
- `Conflict`：多个权威事实互相矛盾。

`FactAvailabilityRule` 对 `Unavailable` 产生 `HOLD`，对 `Conflict` 产生 `MANUAL_REVIEW`。查询失败永远不能被解释为检查通过。

### 砍掉的备选方案

没有使用 `null`、默认安全值或“查询失败后继续自动完成”。这些做法会混淆“没有风险”和“没有查到风险”。

## 4. 审计成功是资金执行资格的前置条件

### 最终选择

`TriageCase` 是单笔分流的一致性边界，状态只能按以下顺序转换：

```text
RECEIVED → INVESTIGATING → DECIDED → AUDITED
```

只有属于同一订单的决定成功持久化审计后，才可能具备后续执行资格。默认模式仍是 `DECISION_ONLY`，不会真实移动资金。

### 砍掉的备选方案

没有采用“先执行资金动作、稍后异步补审计”。一旦进程在两者之间崩溃，就会出现资金已移动但无法解释原因的不可接受状态。

## 5. 权威数据通过 Port 隔离，题目字段只作为明确 Stub

### 最终选择

客户、资产策略、地址风险、资金、汇率和 Travel Rule 查询都通过应用层 Port。离线材料中的 `fiat_status`、链上确认数和到账金额由名称明确的 `Embedded*StubAdapter` 转换为事实。

生产环境只需替换基础设施 Adapter，领域规则和应用编排不依赖具体银行、链节点或 KYC 厂商。

### 砍掉的备选方案

没有把订单自报字段直接当成生产权威事实。订单内容是不可信输入，真实环境必须查询支付网关、内部账本、链节点和合规系统。

## 6. 提现默认挂起，而不是乐观假设余额充足

### 最终选择

题目材料没有钱包余额和原子资金预留记录，因此 `UnavailableWalletFundsAdapter` 返回 `Unavailable`，提现不能仅凭订单声明自动发币。

### 砍掉的备选方案

没有假设“上游已经校验余额”或“订单创建成功就代表资金已预留”。这种乐观假设会破坏资金守恒，也无法处理并发提现。

## 7. Travel Rule 对缺失信息采用保守语义

### 最终选择

完全缺省 `counterparty` 的旧 fixture 按题目约定视为客户直接交易；一旦显式提供交易对手对象但缺少可靠 VASP 状态，则标记为 `UNKNOWN`，不能推断为非 VASP。

达到阈值但必要对手信息不完整时，订单进入非自动结果。

### 砍掉的备选方案

没有把未知 VASP 状态默认解释成 `NOT_VASP`。真实环境应接入权威 VASP 目录，而不是让模型或本地规则猜测。

## 8. 金额、精度和报价全部使用确定性十进制计算

### 最终选择

金额统一使用 `BigDecimal`，按资产策略规定精度和舍入模式处理。过期报价根据原报价和参考价格计算偏差，偏差不超过策略阈值才允许继续，否则 `REQUOTE`。

### 砍掉的备选方案

没有使用 `double`，也没有让模型估算金额、汇率或滑点。浮点误差和非确定推理都不适合资金计算。

## 9. 订单幂等和资金事件去重分开建模

### 最终选择

使用两层幂等：

- 订单处理层：`orderId + payloadSha256`，相同内容可复用结果，不同内容进入冲突处理；
- 资金事件层：`network + txHash + transferIndex`，防止相同链上事件重复入账。

### 砍掉的备选方案

没有只按 `orderId` 去重，也没有只按 `txHash` 去重。一个订单号可能被不同 payload 重放；一笔交易也可能包含多个独立 transfer。

当前使用进程内存实现，能够演示单进程原子 claim，但不能跨进程恢复。生产版本必须替换为带唯一索引和事务的持久化 Adapter。

## 10. 策略规则与运行机制分离

### 最终选择

业务政策位于 domain policy，运行编排位于 application，文件、HTTP、LLM 和持久化实现位于 infrastructure。

修改一条业务规则不需要修改 Agent Prompt；替换一个外部 Provider 不需要修改领域规则。

### 砍掉的备选方案

没有把策略写进 Prompt，也没有把 Spring、Jackson 或供应商 SDK 放进领域层。Prompt 难以做严格差异审查，基础设施依赖会污染业务模型。

## 11. Web 和 CLI 共享同一个队列执行 Use Case

### 最终选择

`TriageController` 和 `TriageCliRunner` 都直接调用无参的 `RunTriageQueueUseCase.run()`。固定的材料目录、订单文件、结果文件、审计文件、评估时刻和并发度统一由 `DefaultRunTriageQueueService` 初始化；入口适配器不再重复解析或保存这些运行参数。运行时组装通过应用层 `BatchProcessorProvider` 端口反转到基础设施层。

相同的材料目录、审计文件和评估时间复用同一个离线 Runtime，使进程内订单幂等、资金事件去重、案件状态、Agent 预算和熔断状态能够跨 Web 请求保留。串行执行边界位于应用服务，不由 Controller 管理。

### 砍掉的备选方案

没有让 Web 和 CLI 分别 `new OfflineTriageRuntimeFactory`，也没有把文件、Jackson 和 Stub Adapter 的初始化塞进领域服务。前者会形成两套入口编排并让 Web 每次请求重置内存状态；后者会让领域层依赖基础设施。

## 12. 评测优先检查危险自动完成

### 最终选择

基础黄金评测重新运行完整队列，比较结构化 `disposition` 和必要 `reason_codes`，并将 `unsafeAutoCompletions` 作为硬指标。

当前 14 单覆盖制裁地址、风险地址、金额不一致、报价滑点、网络不一致、确认数不足、限额、工具不可用、银行账户不一致和重复资金事件等情况。

### 砍掉的备选方案

没有根据自然语言解释是否相似来打分。解释文本可以调整，资金处置和原因码必须稳定。

基础 14 单只能证明固定样例回归，不能单独证明万单可靠性。扩展评测应增加：

- 阈值前后、报价临界点、确认数临界点等自动生成案例；
- 工具超时、冲突、限流、重试耗尽和熔断等故障注入；
- 订单备注中的 Prompt injection 和恶意字段；
- 相同高风险案例的多次非确定模型运行；
- `p95/p99` 延迟、Token、工具调用数和人工升级率统计；
- “任何未解决事实都不能自动完成”等安全不变量。

## 13. 生产队列、故障隔离与万单运行方案

### 最终选择

离线 Demo 继续使用 JSONL 流式读取和单线程处理，保证实现小而清楚。生产环境将文件输入 Adapter 替换为 Kafka 或具备持久化、消费确认、重试和死信能力的消息队列，领域规则和单笔 `TriageOrderUseCase` 不需要因此改写。

生产消费链路计划为：

```text
Kafka 持久化订单消息
→ Consumer 获取消息
→ 持久化 claim（orderId + payloadHash）
→ 查询权威 Facts
→ 执行确定性 Rules
→ 在事务中保存决定、审计和 Outbox 事件
→ 提交 Kafka offset
→ Outbox 异步投递后续业务队列
```

采用 at-least-once 消费语义，并通过持久化幂等保证重复投递不会重复移动资金。需要保持顺序的消息按稳定业务键分区；订单处理幂等使用 `orderId + payloadHash`，链上资金事件继续使用 `network + txHash + transferIndex`。

### 失败分类与路由

“消费失败”不能全部当成同一种故障，否则外部服务短暂抖动会把人工队列打满。生产环境按以下类别处理：

| 失败类型 | 示例 | 处理方式 |
|---|---|---|
| 输入或业务不可判定 | 恶意格式、payload 冲突、权威事实冲突 | 输出 `INVALID_INPUT` 或 `MANUAL_REVIEW`，投递人工复核队列 |
| 可恢复外部故障 | 超时、429、短暂网络失败 | 有上限重试并指数退避，进入延迟重试队列；预算耗尽后 `HOLD`，不自动放行 |
| 核心共享依赖故障 | 行情、KYC、账本或制裁服务整体不可用 | 熔断并快速暂停受影响的 Consumer/Partition；健康探测成功后再恢复消费 |
| 持久化或审计故障 | 数据库、审计存储不可写 | 不提交 offset、不执行资金副作用，暂停消费并告警 |
| 未知程序异常 | 代码缺陷、无法分类异常 | 记录关联 ID 和最小安全审计，投递隔离/死信队列并告警 |

行情系统整体不可用时，不应该让一万条消息逐条超时，也不应该把全部订单立刻转人工。Circuit Breaker 达到阈值后快速失败并暂停依赖行情的订单消费，保留消息和 offset；独立健康探针确认行情恢复后再恢复。若某类订单不依赖该行情，可以由独立 Topic、Consumer Group 或能力路由继续处理，避免无关业务被全局阻塞。

降级必须保持 fail-closed：可以降级为 `HOLD`、延迟重试或暂停消费，不能降级为跳过事实检查。只有策略明确允许且缓存数据满足来源、版本和最大新鲜度要求时，才可以读取缓存事实；过期行情不能用于自动资金决定。

### 持久化与恢复

生产环境不使用当前的进程内 Map 作为最终状态。以下内容需要持久化：

- 订单处理 claim、payload hash、处理状态和最终结果；
- `TriageCase` 状态与策略版本；
- 链上资金事件唯一键；
- 决定、完整审计、外部证据引用和人工案件；
- Batch/Partition checkpoint、重试次数和下一次执行时间；
- Outbox 事件及其投递状态。

进程在任意位置崩溃后，都应依靠未提交 offset、持久化 claim 和幂等键安全重放，而不是依赖 JVM 内存。决定、审计和 Outbox 应在同一事务边界内提交，避免“钱可以动但没有审计”或“审计存在但后续动作永久丢失”。

### 外部接口高可用

权威事实 Port 可以在基础设施层配置主备 Provider，例如多个行情、链节点或地址风险 API，但自动切换有以下约束：

1. 主备数据源必须具有相同的业务语义、资产标识、精度和时间基准；
2. 每条事实保存 `provider`、`evidenceRef`、观测时间和策略允许的新鲜度；
3. 主源故障后可以切换备源，但两个权威来源同时返回且结果超出容差时必须产生 `Conflict`；
4. 制裁、余额、资金预留等强事实不能通过“取更宽松结果”解决冲突；
5. Provider 的超时、错误率、熔断状态和切换次数必须进入监控与审计。

多数据源提高可用性，但也会引入语义不一致和错误切换风险，因此不能简单采用“谁先返回就信谁”。

### 性能演进顺序

性能优化以压测数据为依据，按以下顺序推进：

1. 建立 1 万、10 万级合成队列压测，记录吞吐、队列积压、p95/p99 延迟、外部调用量和人工升级率；
2. 使用 Kafka Partition 和多个 Consumer 实例做水平扩展；
3. 对单订单内互不依赖的事实查询使用有界并行，并为每个 Provider 配置独立并发上限；
4. 使用有界工作池、背压、限流和批量 I/O，避免无界线程和重试风暴；
5. 对热点参考数据采用带版本和新鲜度约束的缓存；

Disruptor 可以降低进程内事件传递的锁竞争和延迟，但当前工作负载主要受数据库、行情、链节点和合规 API 的 I/O 约束。过早引入 Disruptor 不会消除外部延迟，反而会增加线程模型、事件生命周期、异常传播和顺序保证的复杂度。因此它是压测后的可选优化，不是默认生产方案；优先使用 Kafka 分区、水平扩容和有界工作池。

### 可观测性与自动恢复

无人值守运行至少需要以下指标和告警：

- Topic/Partition lag、消费吞吐和最老消息年龄；
- 每个 Disposition、ReasonCode 和人工升级率；
- 每个 Provider 的 p95/p99 延迟、超时率、错误率和熔断状态；
- 重试队列、死信队列和 `MANUAL_REVIEW` 队列积压；
- 幂等冲突、重复消息和 payload 冲突数量；
- 决定写入、审计写入和 Outbox 投递失败数；
- 自动完成率突然升高或降低等分布漂移；
- LLM 调用量、Token、预算耗尽和停止原因（若启用非关键 LLM 能力）。

恢复消费必须基于健康探测和逐步放量，不能在依赖服务刚恢复时一次性释放全部积压流量。可采用半开熔断、小批量探测和动态限速防止二次雪崩。

### 砍掉的备选方案

没有在本次练习中引入 Kafka、数据库、Outbox、Disruptor、真实多 Provider 和完整可观测平台。原因是这些基础设施会掩盖题目真正要求展示的单笔资金决策、失败关闭、规则边界和审计设计，也无法在有限时间内以生产质量完成。

同时砍掉以下生产方案：

- 所有技术失败立即投递人工队列：会把可恢复故障转化为人工洪峰；
- 外部核心接口故障后继续拉取并逐条等待超时：会放大故障并拖垮线程池；
- 先提交 offset，再异步保存决定：进程崩溃时会永久丢单；
- 无限重试：会制造重试风暴并阻塞新订单；
- 无约束并发或默认引入 Disruptor：在没有瓶颈证据时增加复杂度；
- 多 Provider 结果不一致时选择最宽松结果：违反资金系统的 fail-closed 原则。

## 14. 我故意没有做什么

- 没有连接真实银行、钱包、链节点或资金执行 Provider；
- 没有实现真实退款、发币、合规解冻和人工结案；
- 没有让 LLM 参与最终决定；
- 没有声称 14 个黄金用例可以代表生产万单可靠性；
- 没有为了吞吐牺牲资金事件顺序和幂等；
- 没有引入数据库、分布式队列和完整可观测平台来过度打磨题目范围。
- 没有把技术故障全部推给人工审核，也没有用无限重试掩盖外部依赖故障；

## 15. 接下来做什么

按优先级排序：

1. 从默认运行时断开 LLM 补查，只保留隔离 Demo；
2. 增加万单合成案例、安全不变量和故障注入评测；
3. 将订单 claim、资金事件去重、案件状态、决定和审计持久化；
4. 接入 Kafka、持久化 offset/checkpoint、延迟重试队列、隔离队列和 Outbox；
5. 为所有权威查询 Port 增加超时、有限重试、熔断、限流和快速暂停/恢复机制；
6. 接入经过语义校验的主备 Provider，并建立延迟、错误率、切换率和人工升级率指标；
7. 执行万单压力测试，再根据瓶颈选择水平扩容、有界并行、缓存或 Disruptor；
8. 最后才考虑把 LLM 用于人工材料摘要等非关键辅助能力。
